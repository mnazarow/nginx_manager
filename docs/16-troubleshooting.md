# 16. Решение проблем и FAQ

Начинайте с **Диагностики** (или `nmctl diag -p`) — большинство проблем распознаётся автоматически с объяснением и
исправлением.

## Панель

**Панель не открывается.**
1. `systemctl status nginx-manager` и `journalctl -u nginx-manager -n 50`.
2. `curl http://127.0.0.1:8088/healthz` на сервере. Если отвечает — проблема в сети: firewall (порт панели по
   умолчанию не открывается), `NM_BIND_HOST=127.0.0.1`, облачная security group.
3. Порт занят: `ss -ltnp | grep 8088` — смените `NM_BIND_PORT` в `/etc/nginx-manager/panel.conf`.

**Забыли пароль / потеряли 2FA / заблокировали свой IP.**
`nmctl user passwd admin`, `nmctl user reset-2fa admin`, `nmctl allowlist clear`.

**«Слишком много неудачных попыток».** Подождите время блокировки (15 мин) или перезапустите сервис
(`systemctl restart nginx-manager` — счётчики в памяти сбрасываются).

**403 «Сначала смените временный пароль» или «Политика панели требует двухфакторную аутентификацию».** Это
политика входа, её проверяет сервер: пока пароль временный (новый пользователь или пароль сброшен администратором)
или пока администратор без 2FA при включённом «Требовать 2FA для администраторов», можно только смотреть.
Откройте «Мой профиль», смените пароль или настройте 2FA — права вернутся сразу. Скрипты с API-токеном политика
не затрагивает, но создать новый токен до выполнения политики нельзя.

**403 «Только администратор может добавить в «Свои директивы»: …».** Оператор не может добавлять директивы,
которые читают или создают файлы от root или выполняют код (`include` произвольного файла, журнал вне
`/var/log/nginx`, `*_temp_path`, Lua/Perl/njs) — см. [12](12-security.md#безопасность-сервиса-в-системе). Пишите
журналы в `/var/log/nginx/`, общие фрагменты кладите в `/etc/nginx/snippets/` и подключайте `include snippets/имя.conf;`
либо попросите администратора.

**Нет графиков в реальном времени, «нет связи» в верхней панели.** WebSocket не проходит через прокси перед
панелью. Если панель открыта через свой nginx/другой прокси — добавьте проксирование `Upgrade`/`Connection`
(домен панели, настроенный в самой панели, это уже делает).

## Применение конфигурации

**«Конфигурация не прошла проверку nginx -t».** Окно применения показывает строку с ошибкой, сайт и подсказку.
Частые причины: опечатка в «Своих директивах», имя бэкенда не разрешается в DNS (используйте IP или задайте
резолверы), сертификат удалён с диска, дублирующаяся директива в своих директивах.

**Порт 80/443 занят.** Другой веб-сервер (Apache, Caddy, другой nginx, Docker с пробросом портов).
`ss -ltnp 'sport = :80'` покажет процесс. Остановите его (`systemctl disable --now apache2`) или смените порты сайтов.

**После обновления пакета nginx сайты пропали.** Пакетный менеджер заменил `/etc/nginx/nginx.conf`. Диагностика
покажет «nginx.conf не под управлением панели» — нажмите «Применить конфигурацию». Чтобы этого не происходило на
Debian/Ubuntu, при обновлении отвечайте «оставить текущую версию» (установщик использует `--force-confold`).

**Изменения не вступили в силу.** Проверьте плашку «Не применено» в верхней панели — правки сохраняются, но
применяются кнопкой «Применить».

## Сайты и бэкенды

**502 Bad Gateway.** Nginx не может получить ответ бэкенда.
- «Бэкенды» — состояние серверов; «Журнал ошибок» — категория покажет причину:
  `Connection refused` — приложение не запущено или слушает другой адрес/порт (часто только 127.0.0.1 на другом
  сервере); `No route to host` — сеть/firewall; `Permission denied` на RHEL — SELinux
  (`setsebool -P httpd_can_network_connect 1`, есть исправление в Диагностике); `upstream prematurely closed` —
  падение приложения.
- Проверка с сервера: `curl -v http://10.0.0.5:8080/`.

**504 Gateway Timeout.** Бэкенд не успел ответить за «Таймаут чтения». Найдите медленные URI («Аналитика → Медленные»),
увеличьте таймаут для конкретной локации, а не для всего сайта.

**413 Request Entity Too Large.** Увеличьте «Макс. размер тела запроса» сайта или локации.

**400 Request Header Or Cookie Too Large.** Увеличьте `large_client_header_buffers` (например, `8 32k`) в
«Настройки nginx → Буферы и таймауты».

**«upstream sent too big header».** Увеличьте `proxy_buffer_size` до `32k` (сайт → Проксирование → расширенные).

**Бесконечный редирект (ERR_TOO_MANY_REDIRECTS).** Приложение само перенаправляет на HTTPS, но видит HTTP: передайте
схему — заголовок `X-Forwarded-Proto` передаётся по умолчанию, настройте приложение доверять ему (Django
`SECURE_PROXY_SSL_HEADER`, Laravel `TrustProxies`, Express `trust proxy`). За Cloudflare в режиме Flexible —
переключите Cloudflare на Full (strict).

**Приложение видит IP 127.0.0.1 / IP прокси.** Приложение должно читать `X-Real-IP` или `X-Forwarded-For`.
Если перед nginx есть CDN — настройте «Реальный IP клиента».

**WebSocket отключается через минуту.** Увеличьте «Таймаут чтения» для локации WebSocket (`3600s`) или
отправляйте ping из приложения.

**Неправильные абсолютные ссылки / редиректы на внутренний адрес.** Оставьте «Заголовок Host к бэкенду: как у
клиента» и `proxy_redirect default`; приложение должно формировать ссылки по `Host` и `X-Forwarded-Proto`.

**Кэш не работает (всегда MISS/BYPASS).** Бэкенд отдаёт `Cache-Control: private/no-cache` или `Set-Cookie` — nginx
такие ответы не кэширует. Настройте приложение или «Игнорировать заголовки бэкенда» (осторожно с персональными
данными). BYPASS — сработало правило обхода (cookie, Authorization, `?nocache`).

## Сертификаты

См. таблицу ошибок в [07. Сертификаты](07-certificates.md#частые-ошибки). Перед выпуском используйте
«Проверить домен».

**Браузер показывает сертификат другого сайта.** Домен не входит в сертификат или клиент не передаёт SNI.
Диагностика проверяет покрытие доменов сайта сертификатом.

**Нужен сертификат на `*.example.com` или сервер недоступен из интернета.** Используйте DNS-проверку: учётная
запись DNS-провайдера на странице «Сертификаты» → «Учётные записи DNS», затем выпуск с «Проверка владения доменом:
DNS» ([07](07-certificates.md#wildcard-сертификаты-examplecom)). Wildcard не покрывает сам домен — добавьте и
`example.com`.

**DNS-проверка: «No TXT record found».** Центр сертификации проверил запись раньше, чем она разошлась по
DNS-серверам провайдера. Увеличьте «Ожидание распространения записи» (60–300 с). Если не помогает — домен
обслуживается не этим провайдером: сравните `dig NS example.com` с провайдером учётной записи.

**Сертификаты перестали продлеваться, в «Диагностике» — «certbot не запускается».** Чаще всего системный `python3`
заменён на другую версию (update-alternatives, сборка из исходников), а certbot из пакета собран под исходную.
Верните прежнюю версию по умолчанию или переустановите certbot (`apt install --reinstall certbot python3-certbot`).
Временно продлить можно и вручную: `/usr/bin/python3.X /usr/bin/certbot renew`.

**Нужен другой центр сертификации (лимиты, сбой Let's Encrypt, корпоративный УЦ).** Настройки панели →
«Сертификаты (ACME)» → «Центр сертификации» ([07](07-certificates.md#центр-сертификации)). Новые сертификаты
выпускаются там, выпущенные продлеваются в своём центре.

**«Нет связи с ACME-сервером центра сертификации».** Сервер не может открыть адрес каталога ACME: исходящие
соединения закрыты firewall, нужен прокси, адрес каталога указан с ошибкой. Действующий сертификат не меняется,
попытка повторится через час. Проверьте: `curl -sI https://acme-v02.api.letsencrypt.org/directory`.

**«Аккаунт ACME не найден у центра сертификации».** Центр удалил или деактивировал аккаунт (или пересоздан свой
ACME-сервер). Панель удаляет локальную запись certbot об этом аккаунте и сразу повторяет выпуск с новым аккаунтом —
обычно ничего делать не нужно.

## Уведомления и резервные копии

**Уведомления о событиях не приходят.** Проверьте: выбраны каналы и источники («Настройки панели → Уведомления о
событиях»), уровень события не ниже выбранного, нет действующей тишины для всех правил, не превышен лимит 30 в час.
Кнопка «Отправить проверочное» отправляет в каналы напрямую; ошибки доставки — в журнале «События» (источник
«Оповещения»).

**Выгрузка в S3: «HTTP 403 SignatureDoesNotMatch» или «RequestTimeTooSkewed».** Неверный секретный ключ или
часы сервера расходятся с хранилищем больше чем на 15 минут — включите синхронизацию времени (`timedatectl
set-ntp true`; «Диагностика» проверяет это).

**Выгрузка в S3: 403 AccessDenied / 404 NoSuchBucket / 301 PermanentRedirect.** Нет прав на бакет; бакет не
найден (имя, адресация path-style); бакет в другом регионе — укажите его регион. Кнопка «Проверить хранилище»
поясняет каждый ответ.

**Не удаётся скачать копию из хранилища: «Не удалось расшифровать».** В настройках указан другой пароль
шифрования, чем при выгрузке. Временно укажите прежний пароль, скачайте копию и верните новый.

## Статистика

**Нет статистики сайта.** Проверьте, что у сайта включено «Журнал запросов и статистика» и конфигурация применена;
в «Сервер → Сборщик статистики» журнал `nm-access.log` в состоянии ok и обрабатывается.

**Статистика запаздывает.** Нормальная задержка — 1–3 с (буфер журнала). Большое «отставание» в сборщике означает,
что сервер не успевает разбирать журнал: включите сэмплирование журнала запросов или выключите его хранение.

**Цифры дашборда и stub_status различаются.** stub_status считает все запросы nginx, включая не попадающие в журнал
(health-check панели, `access_log off`, служебный статус).

**База данных растёт.** Уменьшите сроки хранения журнала запросов и поминутной статистики. Место освобождается
постепенно; принудительно — `sqlite3 /var/lib/nginx-manager/nginx-manager.db 'VACUUM'` при остановленном сервисе.

## FAQ

**Можно ли редактировать конфигурацию nginx вручную?** Файлы в `/etc/nginx/nginx-manager` и `nginx.conf`
перезаписываются при каждом применении. Для ручных правок используйте поля «Свои директивы» (сайт, локация,
глобально) или кладите свои файлы в `/etc/nginx/conf.d/` (подключаются, если включено в настройках).

**Поддерживается ли несколько внешних IP?** Да: у сайта есть «IP для прослушивания»; сайты на разных IP могут
использовать одни и те же домены и порты.

**Можно ли управлять несколькими серверами?** Каждый сервер — своя установка. Синхронизация — экспорт/импорт или
REST API.

**Работает ли с nginx в Docker?** Панель управляет nginx на той же машине (файлы, процессы). Для контейнера nginx
смонтируйте `/etc/nginx` и `/var/log/nginx` и задайте `NM_NGINX_BIN` обёрткой `docker exec`; проще запустить
nginx на хосте.

**Нужен ли интернет?** Только для установки пакетов, выпуска сертификатов у публичных центров (Let's Encrypt и др.), уведомлений и определения внешнего IP
(отключается). Панель и браузер работают без внешних ресурсов.

**Как удалить и сохранить сайты работающими?** `uninstall.sh --keep-nginx-config` — конфигурация «замораживается»
и продолжает работать без панели.
